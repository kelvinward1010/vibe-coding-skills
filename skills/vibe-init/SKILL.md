# Vibe Init — per-project config for the shared base

The vibe skills are generic. Everything specific to one project lives in that project's `CLAUDE.md`, under a `## Vibe` section. Other vibe skills read it and let it override their defaults. Run this once per project; re-run to refresh.

## Steps

1. **Check what exists.** Read `CLAUDE.md`, `AGENTS.md`, `README`, `.gitignore`. If a `## Vibe` section already exists, show it and ask whether to update or keep it.
2. **Detect the stack.** Same sources as `vibe-read` step 1 (manifests, lockfiles, framework configs). Monorepo → list each package and ask which ones the workflow covers.
3. **Classify the project type** — one or more of: `web-ui`, `mobile`, `desktop`, `game`, `api`, `cli`, `library`, `infra`, `data/notebook`. This decides which stages apply:

   | Type | UI/UX audit | E2E level |
   |---|---|---|
   | `web-ui` | yes (web rules) | browser (Playwright) |
   | `mobile`, `desktop` | yes, but the web rules in `vibe-uiux-audit` only partly apply — note it | platform runner (Flutter integration_test, Detox, XCUITest…) or none |
   | `game` | no (web rules don't fit) — replace with a manual playtest checklist in *Team rules*: controls feel, HUD readability, settings/remapping, pause/save | engine test runner for game logic (Unity Test Framework, GUT for Godot, Unreal Automation, Vitest/Jest for web games); feel is checked by human playtest, not automated |
   | `api` | no | HTTP-level tests against a running server |
   | `cli`, `library` | no | run the binary / public API end to end |
   | `infra`, `data/notebook` | no | none — use plan/validate commands instead of a coverage target |

4. **Find the commands** — install, dev, build, lint, typecheck, test, coverage, e2e. Read scripts; don't guess. Leave a command out rather than invent one, and list it under *Open questions*.
5. **Ask only what can't be detected** — one question at a time: team rules worth enforcing in review, coverage threshold if the default (90% lines / 80% branches on changed code) doesn't fit, folders that are off-limits (generated, vendored). For `game`: per-frame budget (e.g. 60 fps = 16.6 ms) and target platforms; coverage target applies to game logic only, not rendering/scene code. GDScript has no standard coverage tool — set *Coverage: none (test matrix only)* for GDScript projects.
6. **Match stack packs.** Check the table in the `vibe-stacks` skill and list every pack that applies under *Stack packs*. A stack with no pack → note it under *Open questions* (the user may want one written).
7. **Write the config.** Show the `## Vibe` section to the user, then append it to `CLAUDE.md` (create the file if missing). Never rewrite the rest of `CLAUDE.md`.
8. **Gitignore** — add `.vibe/` to `.gitignore` unless the user wants these files committed.

## Output: `## Vibe` section in CLAUDE.md

```markdown
## Vibe

- Type: web-ui, api
- Stack: Next.js 15, Prisma, Postgres
- Stages: read, plan, dev, test, review, uiux-audit
- Test levels: unit (Vitest), integration (Vitest + test DB), e2e (Playwright)
- Coverage: default
- Stack packs: react-nextjs, sql

| Task | Command |
|---|---|
| Install | `pnpm install` |
| Dev | `pnpm dev` |
| Test | `pnpm test` |
| Coverage | `pnpm test --coverage` |
| E2E | `pnpm e2e` |

### Team rules
- <rule the reviewer must enforce>

### Off-limits
- `src/generated/` — generated by Prisma, don't edit

### Open questions
- <anything not detected>
```

Keep it under ~40 lines. Facts the repo already shows (folder structure, conventions) belong in `.vibe/CONTEXT.md`, not here.
